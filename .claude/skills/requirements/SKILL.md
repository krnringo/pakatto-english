# requirements — 要件定義スキル

実装を始める前に、要件を仕様書として固める。Anthropic公式が推奨する「Claudeに自分をインタビューさせる」パターンに、
Spec-Driven Development(SDD)の「良い仕様書の6要素」を組み合わせたもの。

## 大原則: ユーザーが先に出す

このスキルは"代行"ではなく"聞き出し"。ゴール・優先順位・トレードオフの判断はユーザーの領域。
AIが先回りして要件を埋めない。特に「何を作りたいか」の一次情報と「何を諦めてよいか」の判断は必ずユーザーに聞く。
AIの役割は、ユーザーが言語化していない部分(エッジケース・検証基準・スコープ境界)を掘り出すこと。

## 手順

### 1. 依頼を1文で言い直す

「この機能が完成した状態 = ○○が△△になっていること」をまず自分の理解として提示し、ユーザーに確認する。
ズレがあればここで気づく方が、実装後に気づくより100倍安い。

### 2. AskUserQuestionでインタビューする

**当たり前の質問はしない**。ユーザーがまだ考えていなそうな、難しい部分を掘る:

- **技術的な実装方針**: 既存のどの仕組みに乗せるか、新規に作るか。複数の設計案があるならトレードオフを提示して選ばせる
- **UI/UX**: 画面のどこに何が出るか、エラー時の見え方、ローディング状態
- **エッジケース**: 空・0件・最大件数・権限がない場合・ネットワーク失敗時にどう振る舞うべきか
- **スコープ境界**: 今回やらないことは何か(次フェーズに送ってよいものを明確にする)
- **優先順位**: 複数要件が両立しない時、何を優先するか

一度に大量の質問をしない。核心的な分岐点から順に、選択肢を2〜4個提示する形で聞く(丸投げの「どうしますか?」は禁止)。
ユーザーが答えるまで、その論点については仮定を置いて進めない。

### 3. 仕様書を書く

`docs/specs/{NN-feature}.md` に、以下の6要素で書き出す(採番は既存ファイルの続き):

```markdown
# {NN}. {機能名}

## Outcomes(目的)
この機能が完成した状態を1〜2文で。

## Scope boundaries(範囲)
- やること:
- やらないこと(次フェーズ送り含む):

## Constraints(制約)
技術的・業務的に守るべきこと。

## Prior decisions(既存の決定事項)
すでに決まっていて蒸し返さないこと。関連する過去の仕様書があればリンク。

## Task breakdown(タスク分解)
検証可能な単位で分解する(「モデル→API→UI」ではなく「モデル+テスト→API1本+curl確認→...」)。

## Verification criteria(検証基準)
これが通れば完了と言える具体的な条件。可能ならテストケースの形で
(例: 「メール `user@example.com` はtrue、`invalid` はfalse」)。
```

### 4. 実装は新しいセッションで

仕様が固まったら、要件定義の会話で汚れたコンテキストのまま実装に入らない。
「`docs/specs/{NN-feature}.md` を実装して」という一言で、クリーンな状態から `implement` スキルに引き継ぐ。
