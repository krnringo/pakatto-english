# claude-app-template

新しいアプリ開発リポジトリを始めるときのベーステンプレート。単純コピーで使う(git subtree等の追従なし)。

## この仕組みが解決したい問題

Claudeに「いい感じに実装して」とだけ頼むと、だいたい次のどれかが起きる:

- 何を作れば「完成」なのかが曖昧なまま実装が始まり、後から「思ってたのと違う」になる
- 実装した本人(同じ会話)がそのまま「できました」と自己申告し、見落としに気づけない
- 次に何をすべきかの判断がその場の思いつきになり、再現性がない

このテンプレートは、この3つの問題にそれぞれ対応する道具を1個ずつ用意したもの。
**要件定義(何を作るか決める)・実装(作る)・レビュー(本当にできたか確かめる)を、
あえて別の工程として区切る**のが設計の核。

## 全体像(依頼から完了まで)

```
ユーザーの依頼
   │
   ▼
① requirements スキル ── 「何を作るか」をインタビューして仕様書にする
   │                       (docs/specs/01-xxx.md ができる)
   ▼
   ここで一度会話をリセットして新しいセッションへ
   (要件定義中の雑談・迷いをコンテキストに残さない)
   │
   ▼
② implement スキル ── 仕様書を読み、検証しながら実装する
   │                    (deep-taskが必要なら合流)
   ▼
③ review スキル ── OpenAI Codex(codex exec)に、diffと仕様書「だけ」を見せてチェックさせる
   │                 (実装した本人=Claude Codeには見せない、指摘だけを受け取る)
   ▼
   Claude Codeが指摘をトリアージ(妥当/誤検知/判断保留)して修正
   ▼
コミット
```

矢印1つ1つが「わざと立場を変えている」ところがポイント。①では聞き役、②では作り手、③では
**モデルごと変えた第三者**──同じ会話・同じモデルのまま全部やると、自分が決めたことを自分で検証する
形になり、思い込みに気づけない。

## なぜ3つに分かれているか(それぞれの役割)

### ① requirements(要件定義) — 「決める」係

たとえるなら、家を建てる前の「どんな家にしたいか」のヒアリング。ここを飛ばして
いきなり基礎工事(実装)を始めると、後から「やっぱりリビングはこっちがよかった」が起きる。
このスキルは提案はするが、決めるのはユーザー。ゴールや優先順位はユーザーが先に言葉にし、
AIは「言っていない部分(エッジケースや境界線)」を質問で掘り出す役に徹する。

### ② implement(実装) — 「作る」係

仕様書という設計図ができた後の、実際の工事。ここでのコツは「完成してから1回だけ確認する」の
逆をやること。「壁を1枚立てたら、その場でまっすぐか確認する」ように、小さく作っては都度確認する
単位に分解する。複雑な工事(=難しいタスク)になった時だけ、より詳しい手順書 `deep-task` を呼ぶ。

### ③ review(レビュー) — 「確かめる」係

たとえるなら、自分で書いた文章の誤字は自分では気づきにくいが、他人に読んでもらうとすぐ見つかる、
というやつ。実装した本人(Claude Code、同じ会話の続き)がそのまま検収すると、自分の実装が
正しく見えてしまう(サンクコスト・思い込み)。だから**モデルごと変える**:実装はClaude Code、
レビューはOpenAI Codex(`codex exec`)という別系統のモデルに任せる。Codexは「diffと仕様書だけ」を
見て指摘を出し、ファイルは直接触らない。指摘を実コードと突き合わせて採否を決めるのはClaude Code
の仕事(Codexの指摘を鵜呑みにしない)。`codex`が使えない環境では内部サブエージェント
(`code-reviewer`)にフォールバックする。

### CLAUDE.md と skills はなぜ分かれているか

`CLAUDE.md` は**毎回**読まれる。だから「このプロジェクトで絶対に守ってほしいこと」(テストコマンド、
Gitの作法)だけを書く。一方 `requirements` / `implement` / `review` のようなスキルは**必要な時だけ**
読み込まれる。毎回は要らないけど、要件定義やレビューの場面では必要、という知識をここに置くことで、
普段の会話が長い前置きで埋まらないようにしている。

## 具体例で流れを追う

「お問い合わせフォームに、送信後の確認メールを追加してほしい」という依頼が来たとする。

1. **requirements**: 「確認メールの送信元アドレスは?」「送信失敗時はユーザーにどう見せる?」
   「日本語だけでよいか?」などをAskUserQuestionで聞き、`docs/specs/03-confirm-mail.md` に
   目的・範囲・制約・検証基準(「フォーム送信後、指定アドレスにメールが届くこと」等)を書く
2. **implement**: メール送信処理を1つ作って手元で1通送ってみる → テンプレートを作って中身を確認する
   → フォームと繋いで実際に送信してみる、という3段階で進め、都度確認する
3. **review**: `codex exec review` に diff と `03-confirm-mail.md` だけを渡す。
   「送信失敗時のエラーハンドリングが仕様書に書いた通りになっていない」等の指摘が `$OUT` に書き出され、
   Claude Codeがそれを読んで実コードと突き合わせ、妥当なものだけ拾う
4. 指摘を直して再レビュー → 通ったらコミット

## 使い方(要約)

1. このリポジトリの `CLAUDE.md` `.claude/` `docs/` を、新しいプロジェクトのルートにコピーする
2. `CLAUDE.md` 内の `(...)` 部分(テスト/ビルドコマンド、コードスタイル)をプロジェクトに合わせて埋める
3. あとは通常通り: 曖昧・大きい依頼は `requirements` → `implement` → `review` の順で進む
   (小さく明確な変更はスキップしてよい。詳細は `docs/development-guide.md`)

## オンボーディング手順(具体例: 英語学習アプリをゼロから作る)

「英語学習アプリを作りたい」と思い立ってテンプレートをコピーした直後、実際に何をやるかを順番に追う。
**要件定義スキルは「機能」を決める道具であって、「アプリそのものの土台」を決める道具ではない**ことに注意
(土台がまだ何もない段階では、普通の会話で決めてよい)。

### 0. 事前準備(最初の1回だけ)

`review` スキルは `codex` コマンドを使う。入っていなければここで入れておく:

```bash
! codex login   # 未ログインならブラウザでログインを済ませる
```

(入っていなくてもオンボーディング自体は進められる。実際にレビューが必要になった時に
フォールバック=`code-reviewer`サブエージェントが動くので、後回しでもよい)

### 1. テンプレートをコピーする

```bash
mkdir -p ~/Sites/personal/eigo-app
cp -r ~/Sites/personal/claude-app-template/CLAUDE.md \
      ~/Sites/personal/claude-app-template/.claude \
      ~/Sites/personal/claude-app-template/docs \
      ~/Sites/personal/eigo-app/
cd ~/Sites/personal/eigo-app && git init
```

### 2. アプリの土台を決める(スキル不要、ふつうに壁打ちする)

まだ1行もコードがないので、`requirements` スキル(仕様書を書く道具)はまだ出番がない。
Claude Codeにこう話しかけるところから始める:

> 「英語学習アプリを作りたい。Webアプリで、単語帳・クイズ・進捗管理くらいの機能を考えている。
> 技術スタックの相談に乗ってほしい。」

ここでのポイントは、公式ガイドの「Let Claude interview you」と同じ発想で、Claudeに
技術選定の論点(フロント/バックエンドの構成、DBの要否、ホスティング先、認証の要否)を
質問させ、**自分で決める**こと。決まったら実際に雛形を作らせる(例: `npx create-next-app`)。

```bash
git add -A && git commit -m "chore: 初期雛形(Next.js + TypeScript)"
```

### 3. CLAUDE.md を実際の構成で埋める

雛形ができて初めて、`(...)` の中身(テストコマンド・コードスタイル)が実在する情報になる:

```markdown
## 検証の鉄則
テスト/ビルド/lintの実行コマンド: npm test / npm run build / npm run lint

## コードスタイル
TypeScript strict mode。コンポーネントはfunction宣言、Reactは.tsx
```

### 4. 最初の機能を要件定義する(ここで初めて `requirements` スキルの出番)

> 「単語帳機能(単語を登録して、フラッシュカード形式で復習できる)を作りたい。要件定義して」

`requirements` スキルが起動し、AskUserQuestionで「1枚のカードに表示する情報は?」
「間違えた単語をどう再出題するか?」「単語データは自分で登録/インポートどちらか」等を
聞いてくる。答えると `docs/specs/01-flashcard.md` ができる。

### 5. 新しいセッションで実装する

要件定義の会話をそのまま引きずらない。新しいセッション(`/clear` または新規ウィンドウ)で:

> 「`docs/specs/01-flashcard.md` を実装して」

`implement` スキルが、検証可能な単位(データモデル→1枚のカード表示→復習ロジック→画面接続)
に分解しながら進める。

### 6. レビューする

> 「レビューして」

`review` スキルが `codex exec review` を実行し、`docs/specs/01-flashcard.md` の要件・
検証基準と突き合わせた指摘を出す。Claude Codeがその指摘を実コードと照らして採否を判定し、
妥当なものだけ確認の上で直す。

### 7. コミットして、次の機能へ

通ったらコミット。次は「クイズ機能を作りたい」で手順4に戻る、をアプリが完成するまで繰り返す。

## 中身

| ファイル | 役割 |
|---|---|
| `CLAUDE.md` | 毎セッション読まれる基本ルール(短く保つ) |
| `docs/development-guide.md` | 開発フロー全体の解説 |
| `docs/specs/` | `requirements` スキルが書き出す仕様書置き場 |
| `.claude/skills/requirements/` | 要件定義スキル(インタビュー→仕様書化) |
| `.claude/skills/implement/` | 実装スキル(検証可能な単位への分解) |
| `.claude/skills/review/` | レビュースキル(Codex外部レビュー→Claude Codeがトリアージ) |
| `.claude/agents/code-reviewer.md` | レビュー用サブエージェント(`codex`が使えない環境でのフォールバック) |

## 設計の元ネタ

- Anthropic公式 [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
  (Explore→Plan→Implement→Commit、CLAUDE.mdの書き方、スキル/サブエージェント、アドバーサリアルレビュー)
- Claude Code開発者 Boris Cherny の運用(並列セッション、共有CLAUDE.mdの育て方、permission allowlist)
- Geoffrey Huntley の spec駆動開発(Ralph Wiggum) — 実装前に仕様を書き切る思想
- Spec-Driven Development の「良い仕様書の6要素」(outcomes/scope/constraints/prior decisions/
  task breakdown/verification criteria)
- 手元の `codex-review` スキル(OpenAI Codex CLIで異系統モデルレビューを行う運用)を
  `review` スキルのベースに採用

複雑・曖昧・被害の大きいタスクの実行時は、グローバルスキル `~/.claude/skills/deep-task/` も参照する
(分解・検証・次の一手の判断手順)。
