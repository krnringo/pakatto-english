# 開発ガイドライン

このプロジェクトでの開発の進め方。出典: Anthropic公式ベストプラクティス、Claude Code開発者Boris Chernyの運用、
Geoffrey Huntleyのspec駆動開発(Ralph Wiggum)、Spec-Driven Development(SDD)の要件定義手法を統合。

## 全体の流れ

```
Explore(調べる) → Spec(仕様を書く) → Plan(計画) → Implement(実装) → Verify(検証) → Review(レビュー) → Commit
```

大きい変更・曖昧な依頼ほど左側(Explore/Spec)に時間をかける。小さく明確な変更は右側から始めてよい。
「diffを一文で言い切れるか?」が判断基準(言い切れるなら計画は不要)。

## 1. Explore — 実装前に読む

いきなり書き始めると「動くが求められていないもの」ができる。実装前に:

- 既存の似た実装を1つ探して読む(命名・構造・エラー処理の流儀を踏襲する)
- 変更対象の呼び出し元/参照元を洗う(grep)
- テスト/ビルド/lintの実行方法を確認する(最後に検証する手段がないまま書き始めない)

範囲が広い調査(ログ読み、広範囲grep)はサブエージェントに投げて結論だけ受け取る。生ログを延々自分で読まない。

## 2. Spec — 要件を仕様書にする(`requirements` スキル)

Anthropic公式の推奨: 「Claudeに自分をインタビューさせる」。実装を始める前に、AskUserQuestionで
技術的な実装方針・UI/UX・エッジケース・トレードオフを聞き出し、`docs/specs/{NN-feature}.md` に書き出す。

良い仕様書の条件(SDDの6要素):
1. **Outcomes(目的)** — 何が達成された状態がゴールか
2. **Scope boundaries(範囲)** — 何をやり、何をやらないか
3. **Constraints(制約)** — 守るべき技術的・業務的制約
4. **Prior decisions(既存の決定事項)** — 過去にすでに決まっていること(蒸し返さない)
5. **Task breakdown(タスク分解)** — 検証可能な単位への分解
6. **Verification criteria(検証基準)** — 「これが通れば完了」と言える具体的な条件(テストケース等)

詳細は `requirements` スキル(`.claude/skills/requirements/SKILL.md`)を参照。

仕様が固まったら、**新しいセッションで実装に入る**。要件定義の会話で汚れたコンテキストを持ち込まず、
実装に集中したクリーンな状態で始める(Anthropic公式推奨)。

## 3. Implement — 検証可能な単位で実装する(`implement` スキル)

- タスクは「機能単位」ではなく「単体で正しさを確認できる単位」で切る
  - 悪い例: 「モデル→API→UI→最後にまとめて確認」(検証が1回しかない)
  - 良い例: 「モデル+その場でテスト→APIを1本作りcurlで叩く→残りのAPI→UIをつなぎ画面で確認」
- 複数ステップがあるなら、一番自信がない箇所から着手する(そこが不可能なら計画全体が変わるため)
- 複雑・曖昧・被害の大きい変更(本番設定・データ移行・外部送信・不可逆操作)は
  グローバルスキル `deep-task`(`~/.claude/skills/deep-task/SKILL.md`)の手順に従う

## 4. Verify — 「動くはず」で終わらせない

Claudeが自走できるかどうかは「実行して確認できる手段」があるかで決まる。以下のいずれかを必ず用意する:

- テストスイート(具体的なテストケースを事前に渡す。「メール検証を実装して」ではなく
  「`user@example.com`はtrue、`invalid`はfalse、というテストケースで実装後に実行して」)
- ビルド/lintの終了コード
- スクリーンショット比較(UI変更の場合、デザイン画像と実装後の画面を比較させる)
- 再現手順が「再現しなくなったこと」の確認

**主張と証拠をセットにする**。「修正しました」ではなく「テストが red→green になりました(出力: ...)」。
確認できていないことは「未確認」と正直に書く。

## 5. Review — 別モデル(Codex)にレビューさせる(`review` スキル)

実装した本人(Claude Code、同じコンテキスト)は自分の実装に説得されている。このテンプレートでは、
**実装はClaude Code・レビューはOpenAI Codex CLI(`codex exec`)** という異系統モデルに分担させる。
Codexの出力(指摘一覧)はファイルに書き出させ、Claude Codeがそれを読み取ってトリアージする。

役割分離が本質:
- **Codex** は仕様書・diffを見て指摘を出すだけ(ファイルは直接編集させない)
- **Claude Code** が各指摘を実コードと突き合わせて「妥当/誤検知/判断保留」を判定し、
  ✅の指摘だけをユーザー確認の上で修正する

チェックする内容:
- 仕様書(`docs/specs/{NN}.md`)の要件がすべて実装されているか
- 記載されたエッジケースにテストがあるか
- スコープ外の変更が紛れ込んでいないか

Codexは「見つけたものは指摘する」性質上、些細な指摘も出す。**正しさ・要件充足に関わる指摘だけ拾い、
スタイルの好みは無視してよい**(拾いすぎると過剰設計・不要な防御コード・存在しないケースのテストを生む)。
`codex` コマンドが使えない環境では `.claude/agents/code-reviewer.md` の内部サブエージェントに
フォールバックする(その場合も「実装した本人以外がチェックする」構造は維持する)。

## 6. Commit

- コミットメッセージは "why"(なぜその変更が必要だったか)を書く。"what" はdiffで分かる
- 明示的な指示がない限り `--amend` `push --force` は使わない

## よくある失敗パターン(避ける)

- **キッチンシンクセッション**: 1つのタスクの途中で無関係な作業を挟み、コンテキストが汚れる → 無関係な作業ごとに `/clear`
- **同じ間違いを直し続ける**: 2回訂正しても直らないなら、`/clear`して学びを反映した最初のプロンプトからやり直す
- **CLAUDE.mdの肥大化**: 長すぎると重要なルールほど無視される → 定期的に間引く
- **信じて検証しない**: もっともらしい実装が実はエッジケースを処理していない → 検証できないものは出荷しない
- **無限探索**: 「調査して」とだけ言われ範囲を絞らずに数百ファイル読む → 調査範囲を狭めるか、サブエージェントに切り出す
